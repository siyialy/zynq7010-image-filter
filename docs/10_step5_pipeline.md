## 架构

```
video_timing_gen ──┬──▶ test_pattern ──▶ img_filter_3x3 ──┬─▶ rgb_out
   (640x480@60)    │        (彩条)          (3x3 卷积)     │
                   │                                      │
                   └── hs/vs/de ──[延迟 5 拍]──────────────┴─▶ hs_out/vs_out/de_out
```

### 一个容易踩的坑：同步信号必须跟着数据一起延迟

滤波器有 5 拍流水线延迟。如果 `hs/vs/de` 不跟着延迟，显示器的"行起点"就比数据早 5 个像素——画面整体左移，右边少 5 列，边缘出现错位竖条。

所以代码里把 `hs/vs/de` 用移位寄存器延迟 `LAT=5` 拍，和数据严格对齐。

**那 1 行的延迟（行缓存带来的）为什么不用管？**
因为 `hs` 和 `de` 是"每行重复一次"的周期信号，延迟整整一行等于没延迟；`vs` 延迟一行只相当于整帧上移 1/480 行，肉眼不可见。所以只需要补偿横向的 5 拍。

这个坑很典型，值得写进报告的"设计要点"。

## 为什么这个顶层要设计成这样

`video_pipeline.v` 对外只暴露 4 个信号：`rgb_out / hs_out / vs_out / de_out`——就是一套标准并行视频接口。

**好处**：后面不管板子的 HDMI 是哪种方案，这个文件一行都不用改：

| 板子 HDMI 方案 | 需要额外加的模块 |
|---|---|
| 并行 RGB 进发送芯片（TFP410 类） | 直接连，可能要配几个配置脚 |
| ADV7511（I2C 配置） | 加 I2C 初始化（PS 或 PL 状态机） |
| PL 直驱 TMDS（带 OSERDES） | 加一个 TMDS 编码器模块 |

所以**等你的原理图一到，我只需要写最外面那层"板级封装"，核心逻辑全部已验证**。

## 图片 ROM：`tools/bmp2coe.py`

你没有摄像头，但可以让它显示一张**真实照片**。这个脚本把任意图片转成 Vivado 的 BRAM 初始化文件。

```powershell
# 灰度（推荐，省 BRAM）
python tools\bmp2coe.py 你的照片.jpg -o src\rtl\image_gray.coe --width 320 --height 240 --gray

# 彩色 RGB888
python tools\bmp2coe.py 你的照片.jpg -o src\rtl\image_rgb.coe --width 320 --height 240
```

它会同时输出一张 `_preview.png`，让你先确认缩放裁剪后的效果（等比缩放 + 居中裁剪，不会拉伸变形）。

### 容量必须算清楚（XC7Z010 只有 2.1 Mb BRAM）

| 方案 | 容量 | BRAM36 占用 | 结论 |
|---|---|---|---|
| 640×480 灰度 | 2.46 Mb | 68 块 | ✗ 装不下 |
| **320×240 灰度** | 0.59 Mb | 17 块（28%） | ✓ **推荐** |
| 320×240 彩色 | 1.84 Mb | 50 块（83%） | △ 勉强，会把 BRAM 用光 |
| 256×192 灰度 | 0.39 Mb | 11 块（18%） | ✓ 最省 |

**推荐 320×240 灰度**，RTL 里用"像素复制"放大 2 倍显示到 640×480：

```verilog
// 取源图坐标 = 显示坐标 >> 1，即每个源像素显示 2x2
wire [8:0] sx = x_t[9:1];
wire [7:0] sy = y_t[8:1];
```

这样既省 BRAM，显示也够清晰（评委看到滤波前后的照片对比，效果最直观）。
