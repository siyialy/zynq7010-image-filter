## 架构：为什么必须有行缓存

```
                 ┌──────────────┐
  in_rgb ──────▶ │ RGB → 灰度 Y │──┐
                 └──────────────┘  │
                                   ▼
                 ┌─────────────────────────────┐
                 │ 行缓存 BRAM                 │
       　        │  lb0 = 第 y-1 行            │
                 │  lb1 = 第 y-2 行            │──▶ 同一列的 3 个像素
                 └─────────────────────────────┘        (y-2, y-1, y)
                                   │
                                   ▼
                 ┌─────────────────────────────┐
                 │ 行内移位：左1、左2          │──▶ 3×3 九抽头
                 └─────────────────────────────┘
                                   │
                                   ▼
                 ┌─────────────────────────────┐
                 │ 4 种卷积核并行算，mode 选择 │
                 └─────────────────────────────┘
                                   │
                                   ▼
                              out_rgb
```

**核心矛盾**：图像是"一行一行流过来"的。处理第 y 行第 x 列时，第 y-1 行第 x 列的像素**早就过去了**。所以必须把前两行存起来——这就是行缓存（line buffer）。

**为什么按列地址寻址而不是用循环指针**：地址直接用 x，所以消隐期（没有像素的时段）完全不影响对齐。这是本设计能稳定工作的关键之一。

## 四种模式的数学

设 3×3 窗口为：

```
p00 p01 p02
p10 p11 p12
p20 p21 p22
```

| mode | 名称 | 公式 | 用途 |
|---|---|---|---|
| 0 | 灰度直通 | `p11` | 对照组，看得到"去掉了颜色" |
| 1 | 均值模糊 | `(Σp) × 57 >> 9` | ≈ /9，去噪、平滑 |
| 2 | 高斯模糊 | `(p00+2p01+p02+2p10+4p11+2p12+p20+2p21+p22) >> 4` | 更自然的模糊，权重中间大 |
| 3 | Sobel 边缘 | `\|Gx\|+\|Gy\|`，Gx=右列和−左列和，Gy=下行和−上行和 | 边缘检测 |

**全部只用加法、移位、一个常数乘法**，没有任何浮点、没有除法器——这正是 FPGA 擅长的：25MHz 像素时钟下每拍算完一个像素，640×480@60 全帧实时，且延迟固定。

## 边界怎么处理

用**边缘复制（clamp）**：邻域越界时取最近的边缘像素，而不是补 0。

- 补 0 会让图像四周出现一圈黑边，滤波后变成"假边缘"，Sobel 尤其明显
- 边缘复制没有黑边，这也是 OpenCV 的 `BORDER_REPLICATE` 默认策略

实现上：行首（x==0）把左侧抽头预置成第一个像素；前两行（y<2）用当前行顶替上一行。

## 验证方法：黄金参考对比

```
for 每种模式:
    驱动一帧真实图像（带消隐）
    按到达顺序记录 (out_x, out_y, 数据)
    对每个像素：用独立参考模型按 (out_x, out_y) 重算
               与 DUT 输出逐像素比对
```

**为什么要记录 out_x/out_y 而不是按序号对齐**：如果按序号对齐，"坐标标错 1 个像素"这种 bug 会被掩盖（画面整体平移，数值仍然对）。记录坐标后，坐标和数据都是被验证的对象。

## 调试记录（这段对答辩和"踩坑清单"很有价值）

这个模块我从"能编译"调到"全部吻合"，实际踩了 3 个坑，每个都值得记住：

| # | 现象 | 原因 | 修法 |
|---|---|---|---|
| 1 | 图像整体错位 2 像素 | 行缓存 BRAM 读出有 1 拍延迟，而"当前行"没有对应延迟，三行列号错开 → 画面斜着糊 | 给当前行补 1 拍（`gray_s2`） |
| 2 | 错位变成 1 像素 | 修完 ① 后三行对齐了，但**坐标链**（x/y/de）比数据链快 1 拍，导致 `out_x` 标注比真实中心大 1 | 坐标链再补 1 拍（`x_sb2`），让坐标和 `row_cur` 严格同列 |
| 3 | 最右 1 列数值不对 | 行末进入消隐期，右侧抽头取到消隐数据 0 | 已知边界效应，见下 |

**坑 2 的定位技巧**（值得学）：不去猜，直接写一个诊断 testbench，把图像内容设成"像素值 = 列号"，输出值直接告诉你"这个数来自第几列"，偏移量一眼就能量出来。文件留在 [src/sim/tb_probe.v](../src/sim/tb_probe.v)。

## 已知限制（如实写进报告，反而是加分项）

1. **左右各约 1 列边界效应**：消隐期抽头取到 0，最右 1 列会被邻近像素覆盖。真实显示时视频时序会重新生成 DE，表现为最右 1 列重复，视觉不可见。若要彻底消除，需要在行末插入 2 个"补边像素"，属于后续优化项。
2. **图像整体偏移 1 像素**（x-1, y-1）：流水线结构决定，视觉不可见。
3. **无背压**：本设计假设下游恒 ready（我们自己的 HDMI 时序永远 ready）。若接 VDMA 需要加一层 AXI4-Stream 适配器和 FIFO。

**把"已知限制"写进报告比藏起来好**：评委看到你清楚边界在哪、也知道怎么修，可信度会高很多。

## 资源预估（等综合后填真实数字）

| 资源 | 预估 | 说明 |
|---|---|---|
| LUT | ~600~900 | 行缓存用分布式 RAM（异步读），约 256 LUT |
| FF | ~400 | 各级流水线寄存器 |
| BRAM | 0（可改用 1~2 块） | 当前用 LUTRAM；改成同步读 BRAM 可以进一步省 LUT |
| DSP | 0~3 | 灰度转换的 3 个乘法可能被推断为 DSP |

> XC7Z010 总共约 17,600 LUT / 35,200 FF / 60 DSP / 2.1Mb BRAM，这个滤波核占用很小，后面还能并排放多个核。

## 自己动手改（检验你理解了）

1. **把 mode 1 改成"精确 /9"**：现在用 `×57>>9` 近似（误差 ≤1）。试试能不能用 `(Σ×455)>>12` 做到完全精确。
2. **加一个"锐化"模式**：`out = p11 + (p11 - 高斯)`，即原图减去模糊再放大。这是最简单的 unsharp mask。
3. **挑战题**：加 3×3 **中值滤波**（去椒盐噪声最有效）。需要 9 个数排序，提示：用"三三比较 + 取中"的排序网络，不要写冒泡（太慢）。
